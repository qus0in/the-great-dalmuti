# 과잉 검증 회고

## 상황
메인 작업이 끝나지 않은 상태에서 오케스트레이터가 핸드오프를 직렬 리뷰·수정 단위로 확장했고, 작업자들도 스크립트 결과와 페인 상태를 반복적으로 읽고 재검증했다. 사용자는 "검사나 이런건 다 스크립트한테 맡겨야 하고 하나하나씩 읽을 게 아니잖아", "도대체 뭘 하고 있는 거야 전반적으로"라고 지적하며 회고와 규칙 보정을 요구했다.

## 과제
검증을 무작위 반복이 아니라 근거와 범위가 있는 절차로 정리한다. 기계적으로 판정할 수 있는 항목은 소유자 스크립트에 맡기고, 사람이 읽는 리뷰는 판단이 필요한 1회 범위로 제한한다. 현재 요청 범위 밖의 기존 실패는 별도로 보고하고, 통과시키기 위해 면제하거나 무관한 수정으로 작업 범위를 넓히지 않는다. 세부 절차와 간단한 검증 실행기는 소유 스킬과 그 스크립트, 특히 `.agents/skills/orchestrate/scripts/verify.sh`와 로그에 남기고, 이 문서는 원인·조치·중단 기준만 다룬다.

## 조치
1. `AGENTS.md`에 검증 원칙을 추가해 결정적 검사의 1회 실행, 범위가 정해진 리뷰, 통과 증거 재사용, 관련 입력만 재실행, 요청 범위 밖 확장 금지, 이벤트 기반 상태 확인을 교차 규칙으로 못박았다.
2. `docs/structure.md`에 같은 원칙의 한국어 설명과 이 회고 링크를 추가했으며, 스킬 세부 구현은 복제하지 않았다.
3. 검토자와 작성자를 분리하고, 헤드리스 검증은 워커가, 실행 경로 증거는 실제 실행으로 확인하는 기준은 유지했다. 이 회고를 검증 생략의 근거로 쓰지 않는다.
4. 오케스트레이션·지식 기록·UI 검증 스킬을 원칙에 맞췄다. 검사 실행은 `.agents/skills/orchestrate/scripts/verify.sh`로 모으고, 결과 요약과 실패 로그를 남기도록 했다.

## 결과
과도한 검증의 근본 원인은 고정된 인수 기준과 정지점의 부재, 스크립트가 이미 판정한 증거를 에이전트가 다시 읽는 습관, 직렬 파일 단위 리뷰, 페인 폴링이었다. 이후 검증은 아래 중단 규칙을 충족해야 시작하고, 충족하면 멈춘다.

- 결정적 검사(lint, 테스트, 줄 수, 스크립트)는 해당 소유자 스크립트를 한 번 실행하고, 결과가 통과면 전체 출력을 다시 읽지 않는다. 실패·변경·미해결 항목이 나올 때만 해당 부분을 본다.
- 리뷰는 변경된 파일, 실패한 입력, 명시적 위험이 있을 때만 수행하고, 판단 근거를 확보하지 않은 채 전체 검사를 다시 실행하지 않는다.
- 이미 통과한 증거는 입력이 바뀌지 않으면 재사용한다. 재실행은 관련 편집, 실패, 또는 미해결 항목으로 인한 영향받는 검사에 한정한다.
- 요청 범위 밖의 검증 작업, 브라우저 확인, 추가 리뷰 항목은 만들지 않는다.
- 상태와 보고는 작업 완료, 실패, 또는 다음 결정이 필요할 때만 읽는다. 완료 신호가 없는 동안에는 페인을 폴링하지 않는다.
- 헤드리스 시각 검증과 브라우저 검증은 워커가 맡고, 실행 경로의 증거는 dry-run 텍스트가 아니라 실제 실행 payload로 확인한다.
- 간단한 `.agents/skills/orchestrate/scripts/verify.sh` 러너는 체크포인트마다 명시적으로 실행하고 로그를 남기며, 자동 캐시나 상태 파일에 의존하지 않는다.
- 현재 요청 범위 밖의 기존 실패는 별도로 보고하고, 통과시키기 위해 면제하거나 무관한 수정으로 작업 범위를 넓히지 않는다.
