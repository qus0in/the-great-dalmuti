# 릴리스 0.3.8 — Express·브라우저 게임 완성과 운영 기반

## 개요

0.3 계열의 첫 태그로, 정적 프로토타입(0.2)을 Express 서비스로 진화시켜 브라우저에서 사람 1석이 봇 3석과 한 판을 끝내고(게임 가능 단계 C), 프로필·채팅·참가 코드와 신고·이의제기·관리자 운영 기반까지 갖춘 릴리스입니다. 독자는 나중에 수업자료로 읽는 학습자를 가정합니다.

**실제 범위**: `main` 첫 부모 이력의 0.3 머지 전부 — PR #37, PR #40, PR #45, PR #46, PR #47, PR #49, PR #50, PR #52, PR #54, PR #55 — 만 포함합니다. 태그 대상은 `main`의 0.3.8 끝점(`de0ed70`)이며, 이후 별도 배포·이슈 작업은 포함되지 않습니다.

## 상황 (Situation)

- 0.2까지는 서버·인증·게임 규칙 없이 정적 화면(`dist/`)만 있었고, 이를 서비스로 키우는 구조·서빙·로그인·게임 규칙·저장소 결정이 필요했습니다.
- 0.3.4 이후 감사와 0.3.6–0.3.8 설계 인터뷰에서 프로필·채팅·참가 코드·신고·이의제기·관리자 범위가 확정되어, 패치 분할(프로필 → 채팅 → 운영) 순서로 구현·배포해야 했습니다.
- 사용자 규칙에 따라 패치별 나열이 아니라 기능·관심사 단위(응집도)로 묶어 서술합니다.

## 과제 (Task)

- 10개 머지를 기능 묶음으로 정리하고, 각 묶음에 관련 PR 번호를 근거로 붙입니다.
- 수업 독자가 따라갈 수 있게 결정 기록(ADR-0007·0010·0013·0014·0016·0017)과 검증 근거를 연결합니다.
- 남은 위험을 숨기지 않고 결과에 기록합니다.

## 행동 (Action)

각 항목은 왜(why) -> 무엇(what) -> 어떻게(how) 순으로 설명합니다.

### 구조·서빙과 로그인 (PR #37, PR #40)

- Why: 0.2 미리보기와 0.3 서비스가 한 경로에서 충돌하지 않게 자산 위치와 레이어 배치를 먼저 고정해야 했습니다. 서버를 모르는 초반 학습자가 브라우저에서 로그인부터 통과해야 했습니다.
- What: 레이어 루트(`src/ui`, `src/app`, `src/domain`, `src/infra`)와 의존 방향, `dist/` 동결·`src/ui/public/` 분기, Express 정적 서빙·상태 확인·오류 응답, 4인 게임 도메인 규칙, 브라우저 CDN `supabase-js` 구글 로그인·세션·입장 제어를 마련했습니다. `/`·`/play` 주소 정리와 0.2.1 디자인 이식을 함께 반영했습니다.
- How: ADR-0007(구조·자산 위치)과 ADR-0010(CDN 탑재·브라우저 우선, 서버는 비밀키·토큰 검증만)을 기준으로 삼고, PR 전용 검사로 회귀를 막았습니다.

### 게임 API·저장소·검증 (PR #45, PR #46)

- Why: 가짜 저장소 통과만으로 실제 저장소 통과를 주장하지 않기 위해, 단계별 검증(A→B) 경계를 문서(`docs/0.3-patch-plan.md`)로 고정해야 했습니다.
- What: 게임 진행 API·Supabase 저장소·마이그레이션·요청 기록, `hall`·`play` 정적 뷰 이식, 클라이언트 저장 정책(`docs/storage.md`)을 마련했습니다. 64단계 한도에서 멈추던 자동 진행 정지 결함을 고쳤습니다.
- How: 테스트 전용 익명 계정 4개로 실제 API 2게임을 끝까지 돌려 전적·무토큰 401·31초 무행동 대행·손패 노출 0건을 확인한 뒤 계정·게임을 지웠고, 회귀 검사를 남겼습니다.

### 브라우저 플레이·튜토리얼 (PR #47, PR #49)

- Why: 사람 1석이 브라우저 카드 조작으로 봇 3석과 한 판을 끝내는 단계 C가 0.3의 핵심 약속이었고, 그 위에 무엇을 왜 내야 하는지 알려주는 연습층이 필요했습니다.
- What: `src/ui/public/js` 아래 별도 ES 모듈(axios 호출·상태·실시간 반영·화면 연결)과 카드 선택·내기·패스 흐름을 두고, 튜토리얼 진입(`/play?mode=tutorial`)·봇 3석 고정·서버 추천 카드와 한국어 이유·전적 미기록을 얹었습니다. 힌트와 봇은 같은 보통 달무티 전략을 씁니다.
- How: ADR-0013(테스트 세션 주입 E2E·모듈 배치)과 ADR-0014(서버 추천·이유·전적 제외)를 따랐고, 실제 Supabase 상대 브라우저 E2E로 한 판 완주를 확인했습니다.

### 프로필·채팅·참가 코드 (PR #52, PR #54)

- Why: 사람끼리 모여 못 놀면 채팅이 무용지물이 되므로, 아바타 표시 기반과 함께 같은 방에 들어오는 길을 같은 패치에 넣어야 했습니다.
- What: Supabase 공개 버킷 이미지 저장(PNG·JPEG·WebP, 1MB)·대기실 프로필 카드·채팅과 좌석의 원형 이미지+이름·기본 실루엣과 봇 그림을 마련했습니다. 방 안 실시간 채팅(보관 없음·200자·1초 1개·접이식 패널)과 참가 코드(`/play?code=`)·방장 시작·대기실 실시간 좌석 동기화를 열었습니다.
- How: ADR-0016(프로필·채팅 결정)과 ADR-0017(참가 코드 추가·운영 숨김 배포)을 따랐고, 운영 화면은 설정 1곳(`MODERATION_UI`)으로 끈 채 선출시했습니다.

### 신고·이의제기·관리자 (PR #55, 선행분 PR #52·PR #54)

- Why: 신고 3건 자동 차단이 풀 방법 없이 걸리면 안 되므로, 관리자 페이지와 함께 신고·이의제기·차단을 한 패치로 켜야 했습니다.
- What: 좌석·채팅의 사유 선택 신고(3종)·서로 다른 3명 기준 자동 의심 차단(사진 가리기+채팅 금지)·의심 보존과 위반 삭제 구분·차단 1건당 1회 500자 이의제기·별도 `/admin` 3탭(처리 대기·전체 유저·처리 기록)·한 번에 풀기를 마련하고 노출 설정을 켬으로 바꿨습니다.
- How: ADR-0016 결정 18–35를 구현 기준으로 삼았고, 권한은 `admins` 테이블로 확인하며 서버는 사용자 JWT와 DB 함수로 다루고 서비스 역할은 사용자 목록 읽기와 저장소 처리에만 썼습니다.

### 화면 정리·턴 대행·개발 하네스 (PR #50, PR #52)

- Why: 감사에서 드러난 화면 자잘함과 턴 대행 모호함, 작업 유실·신호 분산 문제를 다음 기능 전에 정리해야 했습니다.
- What: 첫 진입 0.2 예시 제거·손패 일자 겹침·대기실 여백·규칙 줄바꿈·좌석 줄바꿈·100줄 복구, 턴 대행 한 차례 한정·튜토리얼 타이머 없음·안내 문구를 반영했습니다. 단일 ledger·신호 수집·프로젝트 설정 분리·콜백 재전달 힌트를 보강했습니다.
- How: 감사 지적을 화면·규칙·하네스 묶음으로 처리했고, 전용 검사(100줄·레이어·임시 참조 검출)로 품질을 유지했습니다.

## 결과 (Result)

- 10개 머지가 위 6묶음에 모두 근거로 등장하며, 패치별 절은 두지 않았습니다.
- 게임 가능 단계 A(가짜 저장소)·B(실제 저장소)·C(브라우저 한 판)를 충족했고, 0.3.4 이후 튜토리얼·0.3.5 정리·0.3.6–0.3.8 프로필·채팅·운영이 같은 아바타·가림 규칙을 재사용합니다.
- 남은 위험: 채팅 금지는 클라이언트 측 확인입니다(PR #55 본문).
