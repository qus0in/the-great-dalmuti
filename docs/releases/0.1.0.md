# 릴리스 0.1.0 — 개발 환경 세팅

## 개요

The Great Dalmuti 저장소의 `작업 환경과 절차 기반`을 마련한 릴리스입니다. 여러 코딩 에이전트(Claude Code, Codex, OpenCode 등)가 충돌 없이 협업하려면 게임 코드보다 먼저 규칙·절차·배치 체계가 필요합니다. 이 마일스톤은 그 기반을 다졌습니다.

**실제 범위**: 프로젝트 워크플로와 개발 환경의 기초만 포함합니다. 게임플레이 로직은 일부도 구현하지 않았습니다. 또한 특정 패키지·프레임워크 도입을 전제로 하지 않으며, 그에 대한 주장도 하지 않습니다.

## 포함 내용

### 에이전트 규칙과 재사용 스킬

- `AGENTS.md` — 모든 에이전트가 따르는 배치 규칙과 스킬 활용 원칙 (영문, 간결한 명령형).
- `codify` — 지식이 임시 폴더·docs·skills·AGENTS.md 중 어디에 둘지 분류하고, 반복 단계는 스크립트로 만들고, 마지막에 검증하는 절차.
- `orchestrate` — 오케스트레이터·워커 분업: 지시서(brief)를 나눠 배분하고 워커들이 구현·상호 리뷰하고 오케스트레이터가 최종 검토하는 절차와 스크립트.
- `prompt-log` — 규칙·구조·작업 방식을 정한 사용자 프롬프트 원문을 의도·결과와 함께 기록하는 절차.
- `git-flow` — 브랜치 운영: main 보호, dev → PR → main 병합, 초기 부트스트랩 절차와 스크립트.
- `gh-issues` — GitHub 이슈와 마일스톤 규칙(라벨 체계, 이슈 단위)과 생성 절차.

### 배치 체계

- `tmp/<작업>/` — 임시·변하는 것 (초안, 로그, 지시서, 보고, 검토). git에서 제외되며, 문서·스킬·규칙은 여기를 참조하지 않습니다.
- `docs/` — 이 프로젝트의 기본 체계와 구조 (한국어 문서).
- `.agents/skills/<이름>/` — 일반적이고 재사용 가능한 절차 (`SKILL.md`)와 결정적 단계 (`scripts/`).

### dev/main PR 워크플로

- 초기 부트스트랩 단계에서는 `main`에 직접 커밋합니다.
- 이후 모든 작업은 `dev` 브랜치에서 진행하고, 풀 리퀘스트(PR)로 `dev` → `main`에 병합합니다.
- `main`은 protected입니다: 직접 푸시·강제 푸시·삭제 금지, PR 필요(승인 0명, 관리자 강제). 워커는 커밋·푸시를 하지 않고, 오케스트레이터가 최종 검토 후 커밋하고 PR로 병합합니다.

### GitHub 라벨·마일스톤 규칙

- 라벨은 `focus`, `instant`, `tuck`, `frontend`, `design` 다섯 개만 사용합니다.
- 마일스톤은 버전 번호(semver)와 한국어 단계 설명을 함께 붙입니다. 현재 단계는 `0.1.0 개발 환경 세팅`입니다.
- 이슈 하나는 반드시 마일스톤 하나와 라벨 하나 이상을 가집니다.

### 오케스트레이터 역할 분담과 안전한 인수인계

- 오케스트레이터는 일을 나누어 `배분`하고 `최종 검토`만 합니다. 구현과 리뷰는 워커가 담당하고, 리뷰어는 작성자가 아닌 워커가 맡습니다.
- 분배는 백그라운드로 진행하고, 오케스트레이터는 워커를 기다리지 않습니다. 워커가 끝날 때마다 다음 단계를 배분합니다.
- 작업 단위는 워커의 모델 등급에 맞춰 배정하고, 가능하면 작성자와 다른 모델 계열의 리뷰어를 둡니다. 각 워커는 서로 겹치지 않는 파일 범위만 다룹니다.
- 인수인계에서는 신원(workspace/self)을 **실시간 증거로만** 확정합니다. 포커스된 창이나 작업 디렉터리로 신원을 추정하거나, `HERDR_ENV=1`만으로 작업 공간을 확정하지 않습니다. 누락되거나 빈 caller ID는 "워커가 없음"이 아니라 "알 수 없음"이며, 오류와 확정된 빈 목록을 구분합니다.
- 인수인계 시점에 `tmp/<작업>/handoff.md`를 남겨 신원과 근거, 현재 브랜치와 기존 변경, 워커 상태와 확인 시각, 소유 파일, 진행 중 작업, 경로, 미해결 사항과 다음 조치를 적습니다. 인수인계 뒤에는 과거 산출물이 아니라 현재 상태를 다시 확인하고, 바쁘거나 막힌 워커를 방해하거나 중복 배분하지 않습니다.

## 왜 이렇게 했는가

여러 에이전트가 같은 저장소를 동시에  쓰면 파일 충돌, 커밋 꼬임, 규칙 중복이 발생하기 쉽습니다. 이 릴리스는 지식이 어디에 들어갈지, 브랜치가 어떻게 흐를지, 이슈를 어떻게 나눌지, 에이전트가 어떻게 나눠 일할지를 정해 이후 게임 구현이 그 위에서 안정적으로 진행되게 했습니다.

## 결과

- 이 릴리스에는 **워크플로·규칙·스킬이라는 환경 기반만** 들어 있습니다. 게임플레이, 패키지 의존성, 프레임워크 도입은 포함되지 않았습니다.
- 다음 단계(0.1.1: 위키, 자동 위임 등)는 이 릴리스 범위 밖이며, 별도로 진행됩니다.
