# 릴리스 0.1.1 — 학습 문서와 협업 운영 정비

## 개요

0.1.0이 규칙과 절차의 뼈대를 세웠다면, 이번 릴리스는 그 뼈대 위에서 사람이 에이전트와 함께 읽고 따를 수 있도록 학습 문서와 협업 운영을 정비한 것입니다. 수업용 위키로 0.1을 설명하고, 협업 과정에서 실제로 드러난 문제(내장 서브에이전트 위임 사고, 한국어 강조 표기 깨짐, 빈 caller ID 인수인계 오인)를 규칙·스킬·회고로 되짚으며, 이슈 라벨과 보고 형식에 의미를 부여합니다.

**실제 범위**: 학습 문서(위키), 협업 규칙·스킬, 인수인계 절차, 이슈·문서 작성 규칙만 포함합니다. 게임플레이 로직은 일부도 구현하지 않았습니다. 패키지·프레임워크 도입도 전제하지 않습니다.

## 상황 (Situation)

0.1.0 병합 이후 네 가지 공백과 문제가 남아 있었습니다.

- 수업 독자가 0.1.0의 목적과 구성 요소를 스스로 이해할 학습 자료가 없었습니다 (#2).
- 비단순 작업을 별도의 오케스트레이터 요청 없이 자동 분담하는 기본값이 규칙으로 확정되어 있지 않았습니다 (#3).
- 협업 중 실제 사고가 발생했습니다: 스킬 설명의 `via Herdr` 누락과 노출된 내장 협업 API 호출로 위임이 내장 서브에이전트로 흐른 문제(#7), 한국어 강조 `**` 바로 뒤에 조사가 붙어 표기가 깨지는 문제(#6), 빈 caller ID로 "워커 없음"을 오인한 인수인계 문제(#8의 계기).
- 이슈 라벨은 이름만 있고 의미가 없어 우선순위와 영역 해석이 달랐습니다 (#14).

## 과제 (Task)

- 마일스톤 0.1.1(학습 문서와 협업 운영 정비)의 이슈 #2, #3, #6, #7, #8, #14를 처리합니다.
- 규칙 변경은 리뷰를 거친 PR로 병합(PR #5, PR #9)하고, 학습 자료는 위키로 게시합니다.
- 사용자의 마무리 요청("우선 0.1.1 마무리")에 맞춰 이 릴리스 문서(`docs/releases/0.1.1.md`) -> 태그 `v0.1.1` -> GitHub Release 본문의 흐름으로 0.1.0과 같은 방식 마감합니다.

## 행동 (Action)

각 항목은 왜(why) -> 무엇(what) -> 어떻게(how) 순으로 설명합니다.

### 수업용 0.1 위키 게시 (#2)

- Why: 0.1.0의 구성 요소가 이후 수업 독자에게 설명되어야 했고, 규칙·스킬·문서의 목적과 협업 절차가 한곳에서 안내될 필요가 있었습니다.
- What: 위키 페이지 `0.1`을 작성해 설명 대상 `0.1.0`을 명시하고, 규칙·스킬·문서의 목적과 분담·독립 리뷰·PR·안전한 인계를 설명하며, 출처 링크를 `v0.1.0` 태그에 고정했습니다.
- How: 작성자와 다른 에이전트의 리뷰를 마친 뒤 게시 커밋 `ca9a48d`로 위키를 올리고 이슈를 닫았습니다. 이후 한국어 강조 표기 수정은 위키 저장소에 직접 커밋(`01bf249`)해 반영했습니다. 위키에는 PR 흐름이 없어 이 수정은 PR #9 밖에서 이루어졌고, 저장소 쪽 규칙·회고는 PR #9가 담당했습니다. FIT 라벨 설명을 더한 위키 갱신은 이 릴리스와 함께 게시됩니다.

### 비단순 작업 자동 분담 기본값 (#3, PR #5)

- Why: 오케스트레이터 역할이나 분담을 별도로 요청해야만 협업이 시작되면 비단순 작업이 지연되고, 역할 구분이 실행되지 않았습니다.
- What: `AGENTS.md`, `orchestrate` 스킬의 적용 조건, `docs/structure.md`를 서로 일치시켜 비단순 작업은 자동으로 `orchestrate`로 시작하게 했습니다. 워커가 구현과 독립 리뷰를 맡고 오케스트레이터는 배정과 최종 검토만 하며, 한 단계로 끝나는 단순 답변은 직접 처리합니다.
- How: PR #5로 병합(2026-10-15)했습니다. 작성자와 다른 에이전트의 리뷰 승인, codify index/check 통과, 관련 요청 프롬프트 원문 기록까지 확인했습니다.

### 한국어 강조 표기 규칙과 회고 (#6, PR #9)

- Why: 한국어 강조 바로 뒤에 조사·어미가 붙으면 `**` 표시가 깨져 문서와 응답에서 마크다운 기호가 그대로 노출되었고, 저장소 릴리스 문서와 위키에도 해당 표기가 있었습니다.
- What: 조사·어미가 이어지는 경우 인라인 코드 또는 HTML 렌더링이 지원되는 `<strong>` 태그로 대체하는 규칙을 공통 규칙(AGENTS.md), codify 작성 지침, 한국어 문서, 위키에 반영했습니다.
- How: 제보 경과와 원인을 `docs/retrospectives/2026-10-15-korean-emphasis.md`에 회고하고, 독립 리뷰와 문서 검사를 거쳐 PR #9로 병합해 이슈를 닫았습니다.

### Herdr 전용 위임 경로 정정과 원인 회고 (#7, PR #9)

- Why: 스킬 설명에서 `via Herdr` 문구가 빠지고 실행 환경에 노출된 내장 협업 API를 쓰면서, Herdr 워커가 준비되어 있어도 내장 서브에이전트로 위임하는 사고가 발생했습니다.
- What: 위임은 Herdr 워커 페인 전용이며 내장 서브에이전트 API로 대체할 수 없다는 것과, 인계 시 `backend=Herdr` 검증 기준을 AGENTS.md, `orchestrate` 스킬, 인계 기준, 구조 문서에 명시했습니다.
- How: 원인 회고를 `docs/retrospectives/2026-10-15-herdr-delegation.md`에 남기고, Herdr worker4 작성, worker3 독립 리뷰 2회 통과와 오케스트레이터 최종 검토를 거쳐 PR #9로 병합해 이슈를 닫았습니다.

### 안전한 오케스트레이터 인수인계 스킬 (#8)

- Why: 빈 caller ID로 "워커 없음"을 오인하거나 포커스·작업 디렉터리로 신원을 추정하면 잘못된 인수인계가 발생합니다. 수작업으로 이어오던 인계 기록·검증을 자동화할 규칙 단위가 필요했습니다.
- What: 신규 스킬 `handoff`(`.agents/skills/handoff/`)를 만들었습니다. 라이브 증거로 `tmp/<작업>/handoff.md` 기록을 남기는 `snapshot.sh`와, 신원과 상태 변화(워커·HEAD·미처리 단위)를 재검증하는 `takeover.sh`가 핵심이며, `orchestrate`의 인계 절차는 이 스킬을 가리키는 포인터로 축소했습니다. 신원은 프로세스 조상의 에이전트 종류와 세션 값이 Herdr 페인 메타데이터와 일치하는 실시간 증거로만 확정하고, `HERDR_ENV=1`만으로는 아무것도 단정하지 않습니다.
- How: Herdr worker4가 구현하고 worker3가 독립 리뷰를 수행했습니다(VERDICT: pass, 1건의 minor — 태스크 이름의 `..`가 `tmp/<작업>/` 격리를 벗어날 수 있음). 이어서 진행된 Fix round 1에서 두 스크립트 모두 태스크 이름 검증을 강화해 경로 이탈 시 exit 2로 차단하고(`snapshot.sh ../x --dry-run`, `takeover.sh ../x` 모두 exit 2), `sh -n`, codify check, `git diff --check`까지 확인했습니다. 이후 커밋 `00e778c`로 저장소에 반영되었고, 이슈는 이 릴리스 PR에서 닫습니다.

### 이슈 라벨 FIT 정의와 문서·보고 작성 규칙 (#14)

- Why: 라벨(focus·instant·tuck·frontend·design)은 이름만 있고 의미가 없어 우선순위와 영역이 혼동됐습니다. 사용자는 FIT 프레임워크로 업무를 분류하고, 설명은 why -> what -> how 순, 완료된 작업의 구성은 STAR 또는 SWOT를 선호합니다. 이 취향을 룰·스킬·문서·위키와 이후 이슈 관리·보고에 일관되게 반영해야 했습니다.
- What: 우선순위 축 focus = 해당 마일스톤의 핵심 작업, instant = 바로 끝낼 수 있는 작고 빠른 작업, tuck = 접어 두는 후순위·보류 작업, 영역 축 frontend = 화면 구현(HTML·CSS 등), design = 시각·디자인 시스템으로 정의하고, 이슈마다 우선순위 라벨 1개와 해당 영역 라벨을 붙이기로 했습니다. 설명 순서는 why -> what -> how, 완료된 작업 보고(리포트·회고·PR 요약)는 STAR, 선택안·설계 평가는 SWOT로 정하고 문서마다 하나만 택하게 했습니다.
- How: `AGENTS.md`에 why -> what -> how 설명 순서와 STAR/SWOT 정책을 추가하고, 이슈 규칙을 FIT 정의와 현재 마일스톤 `0.2.0 = HTML·CSS 프로토타입 화면 구성`으로 갱신했습니다. `gh-issues` 스킬에 FIT 라벨 의미를 기록하고, `issue.sh`는 FIT 라벨이 정확히 1개가 아니면(0개 또는 2개 이상) exit 1로 거부하도록 검증을 넣었습니다. `orchestrate` 스킬(지시서 = why/what/how, 보고/리뷰 = STAR), `codify` 스킬(문서 작성 순서), `docs/structure.md`의 작성 방식·이슈 운영 절, 위키 `0.1`의 라벨 문장을 FIT 설명으로 바꾸는 갱신까지 마쳤습니다(위키 갱신은 이 릴리스와 함께 게시). 이슈 본문 7건(why/what/how 형식) 초안과 프롬프트 원문 3건 기록, 독립 리뷰도 함께 완료했습니다.

## 결과 (Result)

- 병합과 종료: PR #5(#3 종료), PR #9(#6·#7 종료), 위키 0.1 게시(#2 종료). 한국어 강조와 Herdr 위임 사고는 회고 2편(`docs/retrospectives/`)으로 남겼습니다.
- 신규 산출물: `handoff` 스킬(스냅샷·테이크오버)과 관련 규칙 연계, 수업용 위키, 관련 사용자 요청의 프롬프트 원문 기록.
- 릴리스 시점의 마감 상태: #8은 구현·리뷰·경로 격리 수정을 거쳐 커밋 `00e778c`까지 마쳤고, #14는 FIT 라벨 정의와 `issue.sh`의 정확히 1개 FIT 검증, why -> what -> how·STAR/SWOT 규칙, 위키 FIT 문장 갱신을 최종 보고·리뷰까지 마쳤습니다. 두 이슈(#8·#14)는 이 릴리스 PR에서 함께 닫습니다.
- 범위 제한: 이 릴리스에는 문서·규칙·스킬만 들어 있습니다. 게임플레이 코드, 패키지 의존성, 프레임워크 도입은 포함되지 않았습니다. 다음 단계인 0.2.0(HTML·CSS 프로토타입 화면 구성, 이슈 #10~#13, #15)은 이 릴리스 범위 밖입니다.
