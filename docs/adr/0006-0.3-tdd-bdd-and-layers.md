# ADR-0006: 0.3 구현 방법 — TDD·BDD와 4레이어

- 상태: accepted (채택·구현 머지됨, PR #45~#49)
- 날짜: 2026-10-15
- 관련: [ADR-0001](./0001-0.3-play-scope.md) (플레이 범위), [ADR-0002](./0002-0.3-rendering.md) (렌더링), [ADR-0005](./0005-0.3-migration-boundaries.md) (레이어 역할과 이관 경계)
- 이력: 닫힌 이슈 #26, #27, #32, #33
- 출처: 사용자 지시 — "구현에 있어서 tdd, bdd, ui/app/infra/domain 레이어를 도입함"

## Why

0.3 구현이 시작되며 무엇을 먼저 만들고(테스트), 코드를 어디에 두는지(레이어)의 기준이 명시적이어야 한다. 레이어의 역할과 의존 방향, 이관 경계는 [ADR-0005](./0005-0.3-migration-boundaries.md)에 이미 고정되어 있고 [ADR-0001](./0001-0.3-play-scope.md)·[ADR-0002](./0002-0.3-rendering.md)의 공통 제약으로도 남아 있으나, 테스트 방식(TDD·BDD)은 어디에도 기록이 없었다. 본 ADR은 레이어 도입을 선언하고, TDD·BDD를 실행 기준으로 고정한다.

## What

### 확정 결정

1. `ui` / `app` / `domain` / `infra` 4레이어를 0.3 구현 전체에 도입한다. **레이어를 위에 두고 그 아래 도메인/피처를 작성한다**(`app/auth`처럼) — 사용자 원문: "레이어를 위에, 그 아래 도메인/피쳐를 작성 (app/auth 처럼.)" ([0.3 계획 프롬프트 로그](../prompt/2026-10-15-34-plan-0-3-ssr-express-supabase.md), [#26](https://github.com/qus0in/the-great-dalmuti/issues/26)의 "레이어 위·피처 아래"와 동일). 각 레이어의 역할·의존 방향·포트 정의는 [ADR-0005](./0005-0.3-migration-boundaries.md)에 따른다.
2. TDD를 도입한다. 도메인 규칙과 애플리케이션 흐름은 **실패하는 테스트를 먼저 만든 뒤** 구현으로 통과시킨다. 테스트 없는 기능 코드는 만들지 않는다.
3. BDD를 도입한다. 플레이어가 겪는 흐름(참가, 차례 이동, 카드 내기, 승격, 패스, 끊김 재접속)을 사람이 읽는 시나리오 문장으로 먼저 적고, 그 시나리오가 검증되도록 테스트를 구성한다. 달무티 규칙(같은 숫자는 낮은 카드 우선, 계급별 인원 배정 등)은 시나리오 목록으로 관리한다.
4. 레이어 도입과 테스트 도입은 함께 지킨다. 레이어 위반(의존 역행, 도메인의 프레임워크 의존)은 테스트로 잡지 않고 정적 검사로 잡는다(→ [#27](https://github.com/qus0in/the-great-dalmuti/issues/27)).
5. 테스트 러너는 내장 `node:test`를 사용하고, BDD 시나리오는 Given/When/Then `describe`/`it` 이름으로 작성한다. 테스트 의존성을 추가하지 않는다.
6. CI는 GitHub Actions로 모든 PR에 `node --test`를 돌린다. 커버리지 기준은 두지 않으며 TDD 규칙이 대신한다.
7. domain/app 테스트는 포트의 인메모리 페이크를 사용한다. infra의 Supabase 어댑터는 최대한 얇게 두고 실제 프로젝트 대상 수동 E2E로 확인하며, CI에 Supabase 비밀값을 넣지 않는다.
8. 브라우저 화면 검증은 0.2 `ui-prototype` 스킬의 `check.sh`·`shot.sh`를 워커가 실행해 재사용하고, BDD 시나리오 목록을 따라 수동 E2E로 확인한다. Playwright나 새 테스트 의존성은 도입하지 않는다.

### 미결 (임의 결정 금지)

없음. 커버리지 기준·CI 범위·infra 테스트 규칙·UI 검증 방식은 각각 확정 6·7·8항에 해당한다.

### 대안 비교 (작성자 분석, 사용자 결정 아님)

| 대안 | 강점 | 약점 | 기회 | 위협 |
| --- | --- | --- | --- | --- |
| TDD·BDD + 4레이어(확정) | 규칙 변경 시 안전, 이관·리뷰 용이 | 초반 속도 저하 | 시나리오가 곧 문서 | 과도한 시나리오 분해 |
| 테스트 후행(미채택) | 초반 속도 | 회귀 포착 지연 | 없음 | 레이어 붕괴 은폐 |

## How

- 이슈 매핑: [#26](https://github.com/qus0in/the-great-dalmuti/issues/26) 프로젝트 골격과 구조·의존 규칙, [#27](https://github.com/qus0in/the-great-dalmuti/issues/27) 코드 규칙 검사 스킬(100줄·레이어 의존), [#32](https://github.com/qus0in/the-great-dalmuti/issues/32) 도메인 규칙과 테스트.
- 레이어 경계 상세는 [ADR-0005](./0005-0.3-migration-boundaries.md), 화면·배포 제약은 [ADR-0002](./0002-0.3-rendering.md)에 따라 본 문서에 중복 기록하지 않는다.
- 본 ADR은 이슈를 변경하지 않는다.
