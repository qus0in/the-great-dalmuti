# ADR-0008: 0.3 코드 규칙 — ES6+ 린트·브라우저·검증·예외·비동기

- 상태: accepted
- 날짜: 2026-10-16
- 관련: [ADR-0005](./0005-0.3-migration-boundaries.md), [ADR-0006](./0006-0.3-tdd-bdd-and-layers.md), [ADR-0007](./0007-0.3-structure.md)
- 관련 이슈: [#27](https://github.com/qus0in/the-great-dalmuti/issues/27), [#30](https://github.com/qus0in/the-great-dalmuti/issues/30), [#33](https://github.com/qus0in/the-great-dalmuti/issues/33), [#34](https://github.com/qus0in/the-great-dalmuti/issues/34)
- 출처: ES6+ 린트 인터뷰 결정 41–58 (2026-10-16, 사용자 선택)

## Why

0.3 마일스톤 구현이 본격화됨에 따라 JavaScript 코드 스타일, 불변성, 복잡도 제한, 브라우저 호환성, 스키마 검증, 에러 처리, 비동기 문법 규칙을 프로젝트 전반에 통일해야 한다. 합의된 규칙이 없으면 레이어 간 구현 스타일이 분산되고, 브라우저 호환성 결함 및 예외 처리 누락이 발생하기 쉽다. 사용자 인터뷰(결정 41–58)에서 확정된 설계 원칙을 단일 진실 원천(SSOT)으로 기록하여 [#27](https://github.com/qus0in/the-great-dalmuti/issues/27), [#30](https://github.com/qus0in/the-great-dalmuti/issues/30), [#33](https://github.com/qus0in/the-great-dalmuti/issues/33), [#34](https://github.com/qus0in/the-great-dalmuti/issues/34) 작업의 기준선으로 삼는다.

## What

### 확정 결정

1. **린트 및 포맷 도구 (결정 41, 45, 49, 50)**:
   - ESLint 플랫 설정(`eslint.config.js`)을 단일 코드 품질 도구로 채택하고 `npm run lint` 및 CI 검사에 연동한다 ([ADR-0006](./0006-0.3-tdd-bdd-and-layers.md)의 테스트 무의존성 원칙과 분리된 devDependency).
   - Prettier(`.prettierrc`)를 코드 포맷터로 추가하고, ESLint와의 규칙 충돌은 `eslint-config-prettier`로 해소한다.
   - Prettier 옵션: 기본값 유지 + `singleQuote: true` (semi true, 2 spaces, printWidth 80) (결정 49).
   - 적용 대상: `src/**/*.js` (서버, 브라우저, 테스트). HTML, CSS, `dist/`, `.agents` 셸 스크립트는 제외한다 (결정 50).
2. **선언 및 모듈 (결정 42, 43, 44)**:
   - `const` 기본, 재할당 시에만 `let` 허용, `var` 절대 금지 (`prefer-const`, `no-var`).
   - 순수 함수 + named export 원칙. 파일당 단일 책임 원칙. 상태는 불변 객체로 전달하고 새 객체를 반환한다.
   - 클래스 사용 금지 (단, 결정 55의 `Error` 상속 예외 클래스 제외).
   - 예외: `src/infra/ai` 안의 외부 라이브러리 클래스 사용([ADR-0018](./0018-0.4-ai-integration.md)).
   - ESM 전용 (CommonJS 금지), named export 전용 (default export 금지), 상대 경로 import 시 `.js` 확장자를 명시한다.
3. **불변성 및 복잡도 (결정 46, 47)**:
   - `no-param-reassign: { props: true }`. 새 값은 스프레드 연산자(`{ ...state }`, `[...arr]`)로 생성한다. 함수 내부 로컬 배열 `push`는 허용하되 `Object.freeze`는 강제하지 않는다.
   - 복잡도 제약: `max-lines-per-function 30`, `complexity 10`, `max-depth 3`, `max-params 3` (코드 파일 100줄 한도 유지).
4. **구문 규칙 (결정 48)**:
   - `eqeqeq` (엄격 동등 비교).
   - `prefer-template` (문자열 템플릿 사용).
   - `prefer-destructuring` + `prefer-arrow-callback` (콜백은 화살표 함수, 최상위는 함수 선언문).
   - `no-unused-vars` + `no-console` (단, 서버 로깅 모듈 경로는 예외 허용).
5. **브라우저 타깃 및 호환성 (결정 51)**:
   - `package.json`에 `browserslist: "cover 95% in KR"` 설정.
   - 브라우저 스크립트(`src/ui/public/**/*.js`)에 `eslint-plugin-compat`을 적용하여 미지원 웹 API 사용 시 에러를 발생시킨다 (트랜스파일러/번들러 미사용).
   - 사용자 원문 맥락: `"브라우저 95% 도달을 위한 옵션 넣기 + zod를 통한 타입 관련 검증. 이후 thymeleaf와의 연동을 고려"`
6. **zod 유효성 검증 경계 (결정 52)**:
   - 서버 경계(`app`/`infra`)에서만 zod 사용: Express 요청 바디와 Supabase 응답 로우 검증.
   - [ADR-0005](./0005-0.3-migration-boundaries.md)의 도메인 순수성 원칙에 따라 도메인 레이어는 순수 JS로 유지한다 (zod 없음). 브라우저는 서버를 신뢰하여 zod 검증을 수행하지 않는다.
7. **Thymeleaf 연동 고려 제약 (결정 53)**:
   - 미래 Spring Boot/Thymeleaf 전환을 고려하되([ADR-0005](./0005-0.3-migration-boundaries.md)의 향후 Spring 전환 참조), 현 단계에서는 구현 없이 호환성 제약만 유지한다.
   - HTML은 정적으로 완전한 형태(Natural Template) 유지, JS는 `data-*` 속성으로만 DOM을 탐색하며 클라이언트 사이드 템플릿 문법을 배제한다.
   - zod 스키마는 향후 Java DTO(Bean Validation)로 이식할 수 있도록 API 계약으로 문서화한다.
8. **예외 처리 및 Problem Details (결정 54, 55, 56)**:
   - RFC 9457 Problem Details (`application/problem+json`: `type`, `title`, `status`, `detail`, `instance` + `code` 확장 필드) 채택 (향후 Spring `ProblemDetail` 매핑).
   - 사용자 지침 원문: `"예외처리를 적극적으로 반영. http status도 적극적으로 사용."`
   - 예외 흐름: 레이어별 에러 타입(도메인 규칙 에러, app 인증/상태 에러, infra Supabase 래핑 에러)을 throw하고, 단일 Express 중앙 에러 미들웨어에서 HTTP 상태 코드와 Problem Details로 매핑한다. 내부 정보 노출 금지, TDD로 예외 커버리지를 확보한다.
   - 클래스 금지 규칙의 단일 예외: `Error`를 상속(`extends Error`)하는 예외 클래스에 한해 허용한다.
   - HTTP 상태 코드 매핑 (결정 56): 201(생성), 204(내용 없음), 400(zod 검증 실패), 401(JWT 부재/무효), 403(권한 없음/좌석·방장 아님), 404(방 없음), 409(턴 아님/버전 불일치/방 가득 참), 410(재시작으로 라운드 종료), 422(규칙 위반/부적법 플레이), 429(속도 제한), 500(예기치 않은 내부 오류), 503(Supabase 장애).
9. **브라우저 에러 인터셉터 (결정 57)**:
   - 단일 axios 인터셉터에서 HTTP 상태/에러 코드를 동작으로 매핑 (401 로그인, 409 재동기화, 422 룰 힌트, 5xx 재시도 안내)하며 한국어 메시지 테이블을 관리한다.
10. **비동기 프로그래밍 (결정 58 핵심)**:
    - `.then` 체이닝 대신 `async`/`await` 프로미스 문법을 적극 선호하고 헬퍼/유틸은 과하지 않은 선에서 적절히 활용한다.
    - 사용자 지침 원문: `"async, await 등 프로미스 문법 적극적 사용. 과하지 않은 선에서 util, helper gka"`
    - 린트 코어 규칙: `require-await`, `no-async-promise-executor`, `no-promise-executor-return` 강제.

### 제안 (공학적 수단, 사용자 명시 선택 아님)

- **헬퍼/유틸리티 배치 원칙 (오케스트레이터/작성자 해석, 사용자 명시 선택 아님)**:
  - 전역 `utils/` 덤프 디렉터리를 만들지 않고, 헬퍼는 레이어별 공통 모듈(예: `src/<layer>/shared/` 또는 피처 내부)에 위치시킨다.
  - 2곳 이상에서 실제로 재사용될 때에만 공통 모듈로 추출하며, 단일 책임 원칙과 레이어 의존성([ADR-0005](./0005-0.3-migration-boundaries.md))을 준수한다.

### 미결 (임의 결정 금지)

- RFC 9457 Problem Details의 구체적인 `type` URI 스키마 (예: `about:blank` vs `https://api.dalmuti.game/errors/<code-slug>`).
- 429 Too Many Requests에 대한 구체적 레이트 리밋 임계값 및 윈도우 수치 (예: IP/JWT당 분당 요청 수).
- axios 인터셉터 한국어 메시지 테이블의 구체적인 UI 문안 상세.

### 대안 비교 (작성자 분석, 사용자 결정 아님)

| 대안 | 강점 | 약점 | 기회 | 위협 |
| --- | --- | --- | --- | --- |
| 단일 ESLint 플랫 설정 + Prettier 연동 (채택, 결정 41, 45) | 품질 검사(ESLint)와 포맷팅(Prettier)의 역할 분리 명확, 최신 플랫 설정 표준 준수, 충돌 방지 보장 | 도구 2개 설정 관리 오버헤드 | `npm run lint` 및 CI 검사 자동화 간소화 | 플러그인 메이저 버전 변경 시 설정 마이그레이션 필요 |
| ESLint 단독 포맷팅 (미채택) | 단일 도구로 패키지 의존성 최소화 | ESLint 스타일 규칙 지원 중단(stylistic 분리) 추세, 포맷팅 성능 및 편의성 저하 | 의존성 단순화 | 포맷팅 규칙 변경에 따른 린트 속도 저하 및 유지보수 부담 |
| 번들러/트랜스파일러 도입 (미채택) | 최신 문법 및 TS 자유로운 사용, 브라우저 호환성 번들링 자동화 | 빌드 단계 필수화로 개발 속도 저하, 0.3 경량 스택 원칙 위배 | 복잡한 프론트엔드 최적화 | 빌드 복잡도 및 디버깅 오버헤드 증가 |

## How

- **구조 및 레이어 연계**:
  - 레이어 의존성 및 순수성은 [ADR-0005](./0005-0.3-migration-boundaries.md), 테스트 방식은 [ADR-0006](./0006-0.3-tdd-bdd-and-layers.md), 디렉터리 배치는 [ADR-0007](./0007-0.3-structure.md)을 따르며 본 문서에서 재결정하지 않는다.
- **도구 파일 및 구현**:
  - ESLint 설정: [eslint.config.js](../../eslint.config.js)
  - Prettier 설정: [.prettierrc](../../.prettierrc), [.prettierignore](../../.prettierignore)
  - 스크립트 및 타깃: [package.json](../../package.json) (`lint`, `format`, `format:check`, `browserslist`)
- **관련 이슈 매핑**:
  - [#27](https://github.com/qus0in/the-great-dalmuti/issues/27): 0.3 개발 인프라/도구 설정 (본 ADR의 ESLint, Prettier, browserslist 구현).
  - [#30](https://github.com/qus0in/the-great-dalmuti/issues/30): 0.3 도메인 모델 구현 (본 ADR의 순수 함수, 클래스 금지, 불변 객체, 에러 상속 예외 준수).
  - [#33](https://github.com/qus0in/the-great-dalmuti/issues/33): 0.3 에러 처리 및 상태 코드 매핑 (본 ADR의 Problem Details, Express 에러 미들웨어, axios 인터셉터 구현).
  - [#34](https://github.com/qus0in/the-great-dalmuti/issues/34): 0.3 API 검증 (본 ADR의 zod 서버 경계 검증 및 DTO 호환성 준수).
