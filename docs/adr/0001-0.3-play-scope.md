# ADR-0001: 0.3 플레이 범위

## Why

0.3 구현이 플레이 방식·방·봇·재접속 같은 범위 결정을 필요로 한다. 확정된 선택을 기록해 구현 기준을 고정하고, 정해지지 않은 항목을 미결로 분리한다. 확정 외의 내용을 결정된 것으로 다루지 않는다.

## What

### 확정 결정

1. 온라인 4인 플레이와 싱글 플레이를 함께 제공한다. 온라인은 각자 Google 로그인 후 같은 방에 참가해 각자의 브라우저에서 한 판을 진행한다. 싱글은 조건식 기반의 낮은 수준 봇과 둔다.
2. 한 판은 총 4석이다. 사람은 1–4명이 참가하고, 남는 자리는 모두 봇이 채운다. 온라인 방의 빈자리도 동일하게 봇이 담당한다.
3. 연결이 끊기면 유예 시간을 준 뒤 봇이 대행한다. 돌아온 원래 인원은 자기 자리를 되찾는다.
4. 끊김 유예 시간은 30초이다. 새로고침·짧은 끊김에 여유를 주기 위한 선택이며, 유예 중 해당 인원의 차례가 오면 진행을 기다린다.
5. 새 인원의 참가는 다음 판부터 허용한다. 판이 진행 중일 때는 원래 참가자의 재접속만 허용하며, 진행 중인 판의 봇 자리를 새 인원이 즉시 대체하지 않는다.
6. 온라인 방 찾기는 공개 방 목록과 초대 링크를 함께 제공한다. 목록에서 찾아 들어가거나 링크로 참가한다.
7. 방 시작은 방장이 시작을 누르면 10초 카운트다운으로 진행한다. 카운트다운 동안 남은 인원은 나가거나 즉시 시작에 동의할 수 있다.
8. 시작에 준비 버튼이나 사전 준비 조건은 없다. 남은 인원 전원이 동의하면 조기 시작하고, 아니면 만료 시점에 시작한다. 떠난 자리와 빈자리는 봇이 채운다.
9. 일정 시간 플레이하지 않으면 게임에서 강제 퇴장시킨다. 네트워크 연결 여부와 무관하며, 이후 봇이 대행하고 원래 인원은 재접속해야 자기 자리를 되찾는다. 계정 로그아웃이 아니다. 30초 기준은 자기 차례가 시작된 시점부터 계산하고, 다른 사람의 차례를 기다리는 시간은 제외한다. 만료까지 플레이/패스가 없으면 강제 퇴장한다.
10. 서버 재시작/배포 시 진행 중인 판은 종료하고 복원하지 않는다. 완료된 누적 전적은 다음 방문에도 유지되며, 로그인·전적 상세는 [ADR-0004](./0004-0.3-session-and-stats.md)에 따른다. 설정 지속성과 로그아웃·세션 파기 여부는 정하지 않았다.

### 미결 사항

아래는 사용자가 정하지 않았으며 임의 결정 금지:

- 차례-안전 봇/복귀 경계와 명시적 나가기 동작
- 설정 지속성, 세션 저장소·백킹 DB·보존 기간, 모드 분류 시점은 [ADR-0004](./0004-0.3-session-and-stats.md) 미결에 따름
- 전송·저장 상세(인증 토큰 전달 등)는 [ADR-0003](./0003-0.3-transport.md) 미결에 따름

### 대안 비교 (작성자 분석, 사용자 결정 아님)

| 대안 | 강점 | 약점 | 기회 | 위협 |
| --- | --- | --- | --- | --- |
| 빈자리 봇 충원(확정) | 소수 인원도 개시 가능 | 봇 품질이 체험 좌우 | 인원 무관 검증 | 매칭 단순화 |
| 유예 후 봇 대행·복귀(확정) | 짧은 끊김에 강함 | 복귀 경계 미정 | 재접속 흐름 확장 | 상태 관리 복잡 |
| 카운트다운 시작(확정) | 이탈·동의 창구 확보 | 대기 10초 발생 | 시작 흐름 확장 | 타이머 동기화 부담 |
| 미행동 강제 퇴장(확정) | 방치 판 해소 | 오판 시 friction | 재접속 흐름과 연계 | 자기 차례 기준 명확 |

## How

- 기존 제약(모든 0.3 작업 공통):
  - 정적 HTML 직접 작성 + Express 정적 서빙/API + axios로 fetching, 브라우저 JS는 별도 파일(ES modules), DOM은 querySelector 계열만. 기존 SSR 계획은 [ADR-0002](./0002-0.3-rendering.md)로 대체되었다.
  - Supabase Google OAuth2 로그인, 서버 측 `.env` 사용, Render 배포(Dockerfile 없음).
  - 클린 아키텍처: `ui` / `app` / `domain` / `infra`, 레이어 위에 피쳐(`app/auth` 형태).
  - 코드 파일 100줄 상한, SOLID·KISS·YAGNI·DRY.
- 이슈 매핑: [#19](https://github.com/qus0in/the-great-dalmuti/issues/19) 구조·코드 규칙, [#20](https://github.com/qus0in/the-great-dalmuti/issues/20) Express SSR, [#21](https://github.com/qus0in/the-great-dalmuti/issues/21) Supabase 로그인, [#22](https://github.com/qus0in/the-great-dalmuti/issues/22) 클라이언트 JS, [#23](https://github.com/qus0in/the-great-dalmuti/issues/23) 도메인 로직, [#24](https://github.com/qus0in/the-great-dalmuti/issues/24) Render 배포.
- 충돌(후속 정합 필요, 이슈 자체는 미변경): [#20](https://github.com/qus0in/the-great-dalmuti/issues/20)의 SSR 수락 기준과 [#19](https://github.com/qus0in/the-great-dalmuti/issues/19)/[#22](https://github.com/qus0in/the-great-dalmuti/issues/22) 내 SSR 조항은 [ADR-0002](./0002-0.3-rendering.md)의 정적 HTML 결정과 충돌하므로, 이슈 문구 정합이 후속 작업으로 필요하다.
