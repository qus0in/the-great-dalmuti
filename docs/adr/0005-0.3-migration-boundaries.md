# ADR-0005: 0.3 이관 경계

- 상태: draft (의도 기록, 인터뷰·리뷰 대기)
- 날짜: 2026-10-15
- 관련 이슈: [#19](https://github.com/qus0in/the-great-dalmuti/issues/19)
- 관련: [ADR-0003](./0003-0.3-transport.md) (전송과 저장), [ADR-0004](./0004-0.3-session-and-stats.md) (세션과 전적)
- 이력: [0.3 계획 프롬프트 로그](../prompt/2026-10-15-34-plan-0-3-ssr-express-supabase.md) (원문의 모듈 80줄 제한은 현재 100줄 제한이 대체)

## Why

사용자가 향후 Spring Boot 서버 이관 시 Redis로 Realtime 대체 예정임을 고려하라고 했다. 0.3에서 이관 구현 없이, 이관 가능한 경계를 고정한다. 확정 외의 내용을 결정된 것으로 다루지 않는다.

## What

### 확정 의도 (사용자 verbatim)

일단 그렇게 하고 나중에 spring boot 서버로 이관 시 redis로 Realtime 대체 예정임을 고려

### 현 경계 (확정 제약)

1. domain은 Express/Supabase와 독립이다.
2. app은 작은 provider-neutral repository/event 포트(게임·전적 저장, 이벤트 발행·presence·시계, 실제 필요 범위)를 정의하고, infra가 Supabase로 구현한다.
3. 브라우저 구독은 infra 어댑터 뒤에 둔다. Supabase SDK 확산을 막는다.
4. JS domain은 Java로 포팅이 필요하며 자동 소스 재사용이 아니다.
5. 안정 HTTP/event 계약, 버전·라운드·플레이어 식별자, 공개/비공개 상태 구분을 권장 설계 제약으로 둔다.
6. 불필요한 포트·프레임워크·범용 이벤트 버스·이중 구현을 도입하지 않는다.
7. 미래 Spring 서버 + Redis는 서버 팬아웃·presence·event 구현을 대체한다. 브라우저향 SSE/WebSocket 게이트웨이는 별도 설계 대상이다.

### 연기 (미결)

Redis Pub/Sub vs Streams, 영속 DB 이관, 인증 제공자 이관, 일정은 연기한다. 0.3에서 Spring/Redis 구현은 없다.

### 대안 비교 (작성자 분석, 사용자 결정 아님)

| 대안 | 강점 | 약점 | 기회 | 위협 |
| --- | --- | --- | --- | --- |
| 이관 경계 고려(확정) | 이관 비용 절감 | 현재 설계 규율 | 점진 이관 | 과도 설계 유혹 |
| 경계 무시(미채택) | 현재 속도 | 이관 시 재작성 | 없음 | 종속 확산 |

### 출처 (확인 1차 자료)

- [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/) (at-most-once·replay 손실 특성, Streams 선택은 연기)
- [Spring WebSocket](https://docs.spring.io/spring-framework/reference/web/websocket.html)
