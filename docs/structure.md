# 저장소 지식 배치 체계

이 저장소는 여러 코딩 에이전트(Claude Code, Codex, OpenCode 등)가 함께 작업하는 것을 전제로 합니다. 지식은 성격에 따라 아래 위치 중 한 곳에 둡니다.

| 위치 | 담는 것 | 독자 |
|---|---|---|
| `tmp/<작업>/` | 영구적이지 않고 바뀌는 것: 초안, 로그, 작업 중 메모, 에이전트 간 인계 자료 | 에이전트 |
| `docs/` | 이 프로젝트에만 해당하는 기본 체계와 구조 | 사람 + 에이전트 |
| `docs/prompt/` | 체계·규칙·작업 방식을 정한 사용자 프롬프트 원문 (`prompt-log` 스킬로 생성) | 사람 + 에이전트 |
| `.agents/skills/<이름>/SKILL.md` | 일반적이고 다른 곳에서도 재활용할 수 있는 절차 | 에이전트 |
| `.agents/skills/<이름>/scripts/` | 결정적으로 표현할 수 있고 토큰 절약에 도움이 되는 단계 | 에이전트 |
| `AGENTS.md` | 스킬 활용 원칙과 위 배치 규칙 | 에이전트 |

## 연결 구조

- `CLAUDE.md`는 `AGENTS.md`를, `.claude/skills`는 `.agents/skills`를 가리키는 심볼릭 링크입니다. 실제 내용은 링크 대상 쪽만 수정합니다.
- `tmp/`는 `.gitkeep`을 빼고 git에서 제외됩니다. 문서, 스킬, 규칙에서는 `tmp/` 경로를 참조하지 않습니다.

## 작성 방식

- 규칙(`AGENTS.md`)과 스킬은 사람이 검토하지 않는다는 전제로 작성합니다. 여러 에이전트가 공유할 수 있도록 특정 도구에 묶이지 않는 표현을 쓰고, 토큰을 아끼도록 영어 명령형 단문으로 간결하게 적습니다.
- `docs/`는 사람이 읽는 문서이므로 한국어 산문으로 작성합니다.

## 기록 절차 (`codify` 스킬)

위 체계에 맞춰 지식을 기록하는 절차 자체도 `.agents/skills/codify` 스킬로 정리되어 있습니다.

1. 지식의 성격을 분류합니다. 휘발성 → 결정적 → 일반 절차 → 스킬 활용 원칙 → 프로젝트 고유 구조 순으로 판단하고, 처음 해당하는 위치에 둡니다.
2. 해당 위치에 기록합니다. 새 스킬은 `new-skill.sh`로 뼈대를 만듭니다.
3. 반복되거나 입력만으로 결과가 정해지는 단계는 스크립트로 옮깁니다.
4. `index.sh`로 `AGENTS.md`의 스킬 목록을 동기화하고, `check.sh`가 `ok`를 출력하는지 확인합니다.

`check.sh`가 검사하는 항목은 다음과 같습니다.

- 심볼릭 링크와 디렉토리 구성
- 스킬의 frontmatter 형식과 본문 길이
- 스크립트 실행 권한
- 스킬 목록 동기화 여부
- `tmp/`에 git으로 추적되는 파일이 있는지
- 문서와 스킬에서 `tmp/` 경로를 참조하는지

외부 영향 스크립트는 입력을 한 번만 만들고 `--dry-run`은 실행자만 바꿉니다(출력 vs 실행). 리뷰어는 dry-run 텍스트가 아니라 실제 실행 경로를 검증합니다(페이로드 바이트 확인, `jq` 등).

## 프롬프트 기록 절차 (`prompt-log` 스킬)

사용자 프롬프트 가운데 규칙, 구조, 작업 방식, 설계 결정을 정한 것은 해당 작업을 마친 뒤 `docs/prompt/<날짜>-<순번>-<슬러그>.md`로 남깁니다. 단순 조회, 상태 확인, 사소한 수정은 기록하지 않습니다.

- 원문은 번역하거나 고치지 않고 그대로 보존합니다. 비밀 정보만 `[REDACTED]`로 가립니다.
- 각 항목에는 원문, 결과 파일 경로, 의도를 적습니다.
- 생성은 `add.sh`가 맡고, 목록(`docs/prompt/README.md`)은 `index.sh`가 자동으로 만듭니다.
- 목록이 어긋나면 `codify`의 `check.sh`가 잡아냅니다.

## 작업 분담 (orchestrate 스킬)

여러 에이전트가 함께 작업할 때는 `orchestrate` 스킬의 분담 모델을 따릅니다.

- **역할 구분**: 오케스트레이터는 일을 나누어 배분하고 최종 검토만 담당합니다. 실제 구현은 워커 에이전트가 맡습니다.
- **리뷰 방식**: 리뷰는 오케스트레이터가 아니라 워커들끼리 서로 수행하며, 리뷰어는 작성자가 아닌 워커가 맡습니다.
- **파일 소유**: 각 워커는 서로 겹치지 않는 파일 범위만 다루도록 지시합니다.
- **결과 전달**: `tmp/<작업>/` 디렉터리에 `brief-<워커>.md` 지시서, `report-<워커>.md` 결과 보고, `review-<리뷰어>.md` 검토 결과를 주고받습니다. 이 파일들은 작업이 끝나면 사라지는 임시 자료입니다.
- 단일 단계로 끝나는 단순한 작업은 분담 없이 바로 진행합니다.
- **백그라운드 실행**: 오케스트레이터는 작업을 계속 재분배해야 하므로 분배 과정 자체를 원칙적으로 백그라운드로 실행하며, 워커를 기다리며 멈추지 않습니다. 워커가 끝날 때마다 바로 다음 단계를 이어서 배분합니다.
- **모델 성향 기반 배분**: 워커가 탑재한 모델의 등급(티어)에 맞춰 작업 단위를 배정하고, 리뷰어는 가능하면 작성자와 다른 모델 계열의 워커가 맡습니다.

## 브랜치 운영 (git-flow 스킬)

원격 저장소는 github.com/qus0in/the-great-dalmuti 입니다. 브랜치 운영은 `git-flow` 스킬을 따릅니다.

- **초기 부트스트랩**: 저장소를 처음 세팅할 때는 `main`에 직접 커밋합니다.
- **개발 흐름**: 이후에는 `dev` 브랜치에서 작업하고, 풀 리퀘스트(PR)로 `dev` -> `main`에 병합합니다.
- **main 보호**: `main` 브랜치는 protected로 설정하여 직접 푸시를 금지합니다.

## 이슈·마일스톤 운영 (gh-issues 스킬)

이슈와 마일스톤 관리는 `gh-issues` 스킬을 따릅니다.

- **마일스톤**: 버전 번호(semver)와 함께 한국어 단계 설명을 붙입니다. 현재 단계는 `0.1.0 개발 환경 세팅` 입니다.
- **라벨**: `focus`, `instant`, `tuck`, `frontend`, `design` 다섯 개만 사용합니다. 기존에 있던 라벨은 없애고 이 다섯 개로만 배치합니다.
- **이슈 단위**: 이슈 하나는 반드시 마일스톤 하나와 라벨 하나 이상을 가집니다.
