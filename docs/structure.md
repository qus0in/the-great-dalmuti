# 저장소 지식 배치 체계

이 저장소는 여러 코딩 에이전트(Claude Code, Codex, OpenCode 등)가 함께 작업하는 것을 전제로 합니다. 지식은 성격에 따라 아래 위치 중 한 곳에 둡니다.

| 위치 | 담는 것 | 독자 |
|---|---|---|
| `tmp/<작업>/` | 영구적이지 않고 바뀌는 것: 초안, 로그, 작업 중 메모, 에이전트 간 인계 자료 | 에이전트 |
| `docs/` | 이 프로젝트에만 해당하는 기본 체계와 구조 | 사람 + 에이전트 |
| `docs/prompt/` | 체계·규칙·작업 방식을 정한 사용자 프롬프트 원문 (`prompt-log` 스킬로 생성) | 사람 + 에이전트 |
| `.agents/skills/<이름>/SKILL.md` | 일반적이고 다른 곳에서도 재활용할 수 있는 절차 | 에이전트 |
| `.agents/skills/<이름>/scripts/` | 결정적으로 표현할 수 있고 토큰 절약에 도움이 되는 단계 | 에이전트 |
| `AGENTS.md` | 스킬 활용 원칙과 위 배치 규칙 | 에이전트 |

## 연결 구조

- `CLAUDE.md`는 `AGENTS.md`를, `.claude/skills`는 `.agents/skills`를 가리키는 심볼릭 링크입니다. 실제 내용은 링크 대상 쪽만 수정합니다.
- `tmp/`는 `.gitkeep`을 빼고 git에서 제외됩니다. 문서, 스킬, 규칙에서는 `tmp/` 경로를 참조하지 않습니다.

## 작성 방식

- 규칙(`AGENTS.md`)과 스킬은 사람이 검토하지 않는다는 전제로 작성합니다. 여러 에이전트가 공유할 수 있도록 특정 도구에 묶이지 않는 표현을 쓰고, 토큰을 아끼도록 영어 명령형 단문으로 간결하게 적습니다.
- `docs/`는 사람이 읽는 문서이므로 한국어 산문으로 작성합니다.
- 설명 구성은 왜(why) → 무엇을(what) → 어떻게(how) 순서로 서술합니다(이슈 본문, 지시서, 결과 보고서, PR 본문, 설명 문서 등).
- 본문 구성은 상황·과제·조치·결과를 다루는 STAR 기법(Situation, Task, Action, Result; 완료된 작업의 보고·회고·요약) 또는 대안 및 설계 평가를 다루는 SWOT 기법(Strengths, Weaknesses, Opportunities, Threats)을 사용합니다. 문서 목적에 맞춰 하나만 선택하며 강제로 둘 다 적용하지 않습니다.
- 한국어 조사나 어미가 강조 바로 뒤에 붙으면 인라인 코드(백틱 한 쌍)를 사용합니다. HTML을 지원하는 렌더러에서는 `<strong>`도 사용할 수 있습니다. 조사 앞에 공백을 넣어 문장을 바꾸지 않으며, 자세한 배경과 확인 범위는 [한국어 강조 표기 회고](retrospectives/2026-10-15-korean-emphasis.md)에 기록합니다.

## 기록 절차 (`codify` 스킬)

위 체계에 맞춰 지식을 기록하는 절차 자체도 `.agents/skills/codify` 스킬로 정리되어 있습니다.

1. 지식의 성격을 분류합니다. 휘발성 → 결정적 → 일반 절차 → 스킬 활용 원칙 → 프로젝트 고유 구조 순으로 판단하고, 처음 해당하는 위치에 둡니다.
2. 해당 위치에 기록합니다. 새 스킬은 `new-skill.sh`로 뼈대를 만듭니다.
3. 반복되거나 입력만으로 결과가 정해지는 단계는 스크립트로 옮깁니다.
4. `index.sh`로 `AGENTS.md`의 스킬 목록을 동기화하고, `check.sh`가 `ok`를 출력하는지 확인합니다.

`check.sh`가 검사하는 항목은 다음과 같습니다.

- 심볼릭 링크와 디렉토리 구성
- 스킬의 frontmatter 형식과 본문 길이
- 스크립트 실행 권한
- 스킬 목록 동기화 여부
- `tmp/`에 git으로 추적되는 파일이 있는지
- 문서와 스킬에서 `tmp/` 경로를 참조하는지

외부 영향 스크립트는 입력을 한 번만 만들고 `--dry-run`은 실행자만 바꿉니다(출력 vs 실행). 리뷰어는 dry-run 텍스트가 아니라 실제 실행 경로를 검증합니다(페이로드 바이트 확인, `jq` 등).

## 프롬프트 기록 절차 (`prompt-log` 스킬)

사용자 프롬프트 가운데 규칙, 구조, 작업 방식, 설계 결정을 정한 것은 해당 작업을 마친 뒤 `docs/prompt/<날짜>-<순번>-<슬러그>.md`로 남깁니다. 단순 조회, 상태 확인, 사소한 수정은 기록하지 않습니다.

- 원문은 번역하거나 고치지 않고 그대로 보존합니다. 비밀 정보만 `[REDACTED]`로 가립니다.
- 각 항목에는 원문, 결과 파일 경로, 의도를 적습니다.
- 생성은 `add.sh`가 맡고, 목록(`docs/prompt/README.md`)은 `index.sh`가 자동으로 만듭니다.
- 목록이 어긋나면 `codify`의 `check.sh`가 잡아냅니다.

## 작업 분담 (orchestrate 스킬)

여러 단계나 검토가 필요한 작업은 사용자가 별도로 오케스트레이터 역할이나 작업 분담을 요청하지 않아도 `orchestrate` 스킬로 시작합니다. 요청을 받은 에이전트는 오케스트레이터로서 작업 단위를 나누고, Herdr 워커가 구현과 교차 리뷰를 맡도록 배정합니다. 구현과 검토의 담당자를 나누어 서로의 판단을 확인하고, 파일 담당 범위를 정해 동시에 작업할 때의 충돌을 줄이기 위한 기본 방식입니다.

작업 분담 수단은 Herdr 워커 페인(`scripts/dispatch.sh`)만을 사용합니다. 실행 환경에 플랫폼 내장 서브에이전트/협동 도구가 보이더라도 이를 위임 수단으로 대체하지 않습니다.

- **Herdr 워커와 내장 서브에이전트의 차이**: 이름이 유사하더라도 동작 방식과 역할이 근본적으로 다릅니다. Herdr 워커 페인은 독립된 세션·도구·작업 이력을 유지하며 Herdr 로스터에 등록되어 서로 다른 모델 계열 간 교차 리뷰가 가능합니다. 반면 내장 서브에이전트는 부모 프로세스에 종속된 일시적 호출 단위로, Herdr 로스터나 상태 추적(`workers.sh`, `wait.sh`)에 잡히지 않아 교차 검증과 인계 추적이 불가능합니다.
- **가용성 확인 및 대응**: 워커 가용성은 실행 환경(`scripts/context.sh`, `scripts/workers.sh`)에서 확인합니다. 확인 실패를 워커 부재로 단정하지 않으며, 환경 확인 불가나 준비된 워커 부재 시에도 내장 서브에이전트로 임의 대체하거나 오케스트레이터가 직접 구현하지 않고 스킬의 탐색 및 보고 절차를 따릅니다.
- **역할 구분**: 오케스트레이터는 일을 나누어 배분하고 최종 검토만 담당합니다. 실제 구현과 교차 리뷰는 Herdr 워커 에이전트가 맡습니다.
- **리뷰 방식**: 리뷰는 오케스트레이터가 아니라 워커들끼리 서로 수행하며, 리뷰어는 작성자가 아닌 워커가 맡습니다.
- **파일 소유**: 각 워커는 서로 겹치지 않는 파일 범위만 다루도록 지시합니다.
- **결과 전달**: `tmp/<작업>/` 디렉터리에 `brief-<워커>.md` 지시서, `report-<워커>.md` 결과 보고, `review-<리뷰어>.md` 검토 결과를 주고받습니다. 이 파일들은 작업이 끝나면 사라지는 임시 자료입니다.
- 단일 단계로 끝나는 단순한 작업은 분담 없이 바로 진행합니다.
- **백그라운드 실행**: 오케스트레이터는 작업을 계속 재분배해야 하므로 분배 과정 자체를 원칙적으로 백그라운드로 실행하며, 워커를 기다리며 멈추지 않습니다. 워커가 끝날 때마다 바로 다음 단계를 이어서 배분합니다.
- **모델 성향 기반 배분**: 워커가 탑재한 모델의 등급(티어)에 맞춰 작업 단위를 배정하고, 리뷰어는 가능하면 작성자와 다른 모델 계열의 워커가 맡습니다.

## 인수인계 절차 (`handoff` 스킬)

오케스트레이터 자리를 다른 에이전트에게 넘기거나, 다른 에이전트가 이어받을 때는 `handoff` 스킬(`.agents/skills/handoff/SKILL.md`)을 따릅니다.

- **두 가지 수단**: 현재 상태를 남길 기록(`scripts/snapshot.sh`)과 인계 시점에 신원·상태 변화를 확인하는 검증(`scripts/takeover.sh`)이 있습니다. 자세한 사용법은 스킬 문서를 따릅니다.
- **실시간 증거 기반 신원**: 신원은 프로세스 조상의 에이전트 종류와 세션 값이 Herdr 페인 메타데이터와 일치하는 실시간 증거로만 확정합니다. 터미널 포커스나 현재 작업 디렉터리만으로 신원을 추정하지 않으며, `HERDR_ENV=1`만으로는 아무것도 증명하지 못합니다.
- **백엔드는 Herdr**: 인계와 위임은 Herdr 워커 페인만 사용합니다. 확인된 백엔드가 Herdr이 아니면 진행하지 않습니다.
- **기록은 증거가 아니라 단서**: 인계 기록은 `tmp/<작업>/handoff.md`에 남기고, 나중에 이어받을 때는 기록을 그대로 믿지 않고 실시간 상태를 다시 확인합니다.

## 브랜치 운영 (git-flow 스킬)

원격 저장소는 github.com/qus0in/the-great-dalmuti 입니다. 브랜치 운영은 `git-flow` 스킬을 따릅니다.

- **초기 부트스트랩**: 저장소를 처음 세팅할 때는 `main`에 직접 커밋합니다.
- **개발 흐름**: 이후에는 `dev` 브랜치에서 작업하고, 풀 리퀘스트(PR)로 `dev` -> `main`에 병합합니다.
- **main 보호**: `main` 브랜치는 protected로 설정하여 직접 푸시를 금지합니다.

## 이슈·마일스톤 운영 (gh-issues 스킬)

이슈와 마일스톤 관리는 `gh-issues` 스킬을 따릅니다.

- **마일스톤**: 버전 번호(semver)와 함께 한국어 단계 설명을 붙입니다.
- **FIT 프레임워크와 라벨 체계**: 라벨은 업무 성격과 우선순위를 분류하는 FIT 라벨 3종과 도메인 라벨 2종만 사용합니다.
  - `focus`: 마일스톤의 핵심 작업
  - `instant`: 즉시 처리 가능한 작은 작업
  - `tuck`: 보류하거나 나중으로 미뤄둔 작업
  - `frontend`, `design`: 도메인 영역을 나타내는 보조 라벨
- **이슈 단위**: 이슈 하나는 반드시 마일스톤 하나와 정확히 1개의 FIT 라벨, 그리고 필요에 따른 도메인 라벨(`frontend`, `design`)을 가집니다. FIT 라벨이 없거나 2개 이상이면 등록되지 않습니다.

## 워크플로우 액션 버전 관리 (`gh-actions` 스킬)

GitHub Actions 워크플로우를 도입하거나 수정할 때는 `gh-actions` 스킬을 따릅니다.

- **이유 (why)**: 예전 템플릿이나 기억에 의존해 액션 버전을 지정하면 오래된 메이저 버전이나 지원 종료된 런타임(Node 등)이 포함되어 보안 취약점과 실행 오류가 발생합니다.
- **내용 (what)**: 워크플로우에 사용하는 모든 액션은 공식 릴리스 기준 최신 안정 메이저 태그(`@vN`)로 고정하며, 런타임 설정(Node/Python/Java 등)은 LTS 버전을 우선 지정합니다.
- **방법 (how)**:
  1. 워크플로우 작성 전 `latest.sh <owner/repo>...`로 대상 액션의 최신 안정 릴리스와 메이저 태그를 조회합니다.
  2. 조회한 메이저 버전(`@vN`)으로 워크플로우를 작성합니다.
  3. 리뷰 요청 전 `check.sh`를 실행하여 워크플로우의 액션들이 최신 메이저 버전을 만족하는지(`ok`) 확인합니다.
